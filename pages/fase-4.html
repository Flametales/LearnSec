TRACK A

Red Team Operator.

12+ MAANDEN · OFFENSIEVE SPECIALISATIE

Simuleer geavanceerde dreigingen tegen organisaties. Niet alleen exploits draaien — onzichtbaar opereren, detectie ontwijken, en de verdediging testen alsof je een echte APT bent.

A

Van penetration test naar red team engagement

Red teaming gaat verder dan vulnerability scanning en exploitation. Het gaat over het simuleren van een volledige threat actor — van initial access tot data exfiltration — terwijl je onzichtbaar blijft voor het blue team.

Kernconcepten

  • Custom C2 Development — Bouw je eigen Command & Control framework. Begrijp hoe bestaande C2s (Cobalt Strike, Mythic, Sliver) werken en waarom custom tooling essentieel is voor geavanceerde engagements.
  • EDR Evasion — Begrijp hoe EDR-oplossingen werken (userland hooking, kernel callbacks, ETW) en hoe je ze kunt omzeilen zonder gedetecteerd te worden.
  • AMSI/ETW Patching — Patch de Antimalware Scan Interface en Event Tracing for Windows om detectie te ontwijken. Begrijp waarom dit werkt en hoe defenders het detecteren.
  • OPSEC (Operational Security) — Het verschil tussen detectie in minuten vs maanden. Elke actie die je uitvoert genereert artefacten — minimaliseer je footprint.
  • Assumed-Breach Scenarios — Begin vanuit een geëstableerd beachhead. Focus op lateral movement, privilege escalation, en data exfiltration.
  • Direct/Indirect Syscalls — Omzeil userland hooking door direct system calls te maken. Begrijp de Windows syscall table en hoe dit evolueert per Windows-versie.
  • Hardware Breakpoints — Gebruik hardware breakpoints voor unhooking en detectie-evasie. Begrijp debug registers en hoe ze werken op CPU-niveau.
  • Infrastructure Rotation — Draai je C2-infrastructuur regelmatig. Gebruik redirectors, domain fronting, en legitimate cloud services om attributie te bemoeilijken.
  • Social Engineering — Phishing, vishing, pretexting. De menselijke factor is vaak de gemakkelijkste weg naar binnen.
Diep Begrip — Red Team vs Penetration Test

Het verschil tussen een penetration test en een red team engagement is fundamenteel en wordt vaak verkeerd begrepen.

Een penetration test is scope-gebonden: test deze applicatie, dit netwerk, deze API. Het doel is zoveel mogelijk kwetsbaarheden vinden binnen een afgebakend doelwit. Tijd is beperkt (meestal 1-2 weken), en het blue team weet vaak dat er getest wordt.

Een red team engagement is objective-gebonden: kun je bij de kroonjuwelen komen? Het doel is niet elke kwetsbaarheid vinden, maar één realistische aanvalsketen uitvoeren. De scope is de hele organisatie. Het blue team weet niet dat je er bent. Rules of engagement bepalen wat wel en niet mag.

OPSEC maakt het verschil tussen detectie in minuten vs maanden. Een penetration tester mag luidruchtig zijn — een red team operator niet. Elke tool die je draait, elke connectie die je maakt, elke file die je aanraakt genereert artefacten. De kunst is om zo min mogelijk sporen achter te laten terwijl je je objectief bereikt.

Dit is waarom custom tooling essentieel is: bekende tools hebben bekende signatures. Als je Cobalt Strike out-of-the-box gebruikt, detecteert elke fatsoenlijke EDR je binnen seconden. Custom C2, custom loaders, custom implants — dat is wat het verschil maakt.

Oefeningen

OEFENING A.1
HARD
Design een covert C2-communicatiekanaal
Ontwerp een C2-communicatiekanaal dat legitiem HTTPS-verkeer nabootst. Documenteer je keuzes voor: transport protocol, jitter/sleep patterns, encryption, en hoe je het verkeer laat lijken op normaal browsegedrag. Teken de volledige infrastructuur: implant → redirector → teamserver.
TOON ANTWOORD
Gebruik domain fronting of legitieme cloud services (Azure, AWS CloudFront) als redirectors. Implementeer jitter en sleep patterns — varieer de callback-intervallen (bijv. 60s ± 30% jitter) zodat het verkeer niet periodiek is. Gebruik malleable C2 profiles om HTTP headers, URI paths, en body encoding te configureren zodat het verkeer op normaal webverkeer lijkt. Encrypt de payload met TLS binnen standaard HTTPS naar een CDN, zodat zelfs deep packet inspection alleen TLS-verkeer naar een legitieme CDN ziet. Voeg random padding toe aan payloads om vaste pakketgroottes te voorkomen.
Bron: SpecterOps · C2 Matrix · Cobalt Strike Malleable C2 Profiles
OEFENING A.2
HARD
AMSI bypass in PowerShell (geïsoleerd lab)
Maak een simpele AMSI bypass in PowerShell — alleen in je geïsoleerde lab. Leg uit hoe de bypass werkt, welke functie gepatched wordt, en waarom dit effectief is. Documenteer ook hoe defenders deze bypass detecteren.
TOON ANTWOORD
De klassieke aanpak patched amsi.dll's AmsiScanBuffer functie om altijd AMSI_RESULT_CLEAN te retourneren. Dit werkt omdat AMSI een userland DLL is die door PowerShell geladen wordt — als je het geheugen van de eigen process kunt aanpassen, kun je de scanfunctie neutraliseren. Defenders detecteren dit via: ETW events (AMSI-gerelateerde ETW providers loggen bypass-pogingen), memory scanning (EDR kan de integrity van amsi.dll in geheugen verifiëren), en script block logging (de bypass-code zelf wordt soms gelogd voordat AMSI gepatched is). Moderne varianten gebruiken indirect patching of hardware breakpoints om detectie te vermijden.
Bron: Rasta Mouse · AMSI.fail · MDSec Research

TRACK B

Malware Analyse & Reverse Engineering.

12+ MAANDEN · ANALYTISCHE SPECIALISATIE

Ontleed malware tot op assembly-niveau. Begrijp hoe exploits werken, hoe rootkits zich verbergen, en hoe firmware gecompromitteerd wordt. De meest technische specialisatie — en de meest tijdloze.

B

Van binary tot begrip

Reverse engineering vereist diep begrip van hoe computers echt werken — op CPU-instructieniveau. Je leert assembly lezen zoals anderen Python lezen, en je begrijpt de internals van besturingssystemen beter dan de meeste developers.

Kernconcepten

  • x86/x64 + ARM Assembly — Lees assembly als een tweede taal. Begrijp calling conventions, stack frames, register gebruik, en control flow op instructieniveau.
  • Windows Internals Deep — PE-formaat, DLL loading, TEB/PEB, structured exception handling, memory management. Het fundament voor malware-analyse op Windows.
  • Kernel Internals — Kernel-mode vs user-mode, system calls, interrupt handling, driver model. Begrijp hoe het OS werkt onder de motorkap.
  • Rootkits — Kernel rootkits, bootkits, hypervisor-level rootkits. Hoe ze zich verbergen en hoe je ze detecteert.
  • Firmware & UEFI — UEFI firmware analyse, secure boot bypass, firmware implants. Het laagste niveau van persistentie.
  • Exploit Development — Heap shaping, JIT spraying, type confusion, use-after-free. Van vulnerability tot werkende exploit.
Diep Begrip — Waarom RE de meest tijdloze skill is

Reverse engineering is de meest technische specialisatie in cybersecurity — en tegelijkertijd de specialisatie die de stabilste carrière biedt.

De reden is simpel: RE gaat over fundamenten, niet over tools. Tools veranderen elk jaar — IDA Pro wordt Ghidra wordt Binary Ninja — maar de onderliggende concepten zijn al decennia hetzelfde. x86 assembly is in de kern niet veranderd sinds de jaren '80. De Windows PE-structuur is stabiel sinds Windows NT. Zelfs als architecturen evolueren (ARM, RISC-V), zijn de principes identiek.

Dit betekent dat elke dag die je investeert in RE compound returns oplevert. Je bouwt kennis die niet veroudert. Een exploit developer die heap shaping begrijpt kan dat begrip toepassen op elke heap allocator, in elk OS, voor de rest van hun carrière.

De keerzijde: de learning curve is steil. Je moet comfortabel zijn met assembly, begrijpen hoe geheugen werkt op byte-niveau, en geduld hebben om uren naar een debugger te staren. Maar als je dit pad kiest en volhoudt, ben je een van de weinige mensen ter wereld die echt begrijpt hoe software werkt.

Oefeningen

OEFENING B.1
HARD
Reverse engineer een crackme binary met Ghidra
Download een simpele crackme binary (bijv. van crackmes.one). Open deze in Ghidra, vind de main() functie, identificeer de password-check logica, en patch de binary zodat elke input geaccepteerd wordt. Documenteer je volledige analyse-proces.
TOON ANTWOORD
Stap 1: Open de binary in Ghidra en laat de auto-analyse draaien. Stap 2: Vind main() via de Symbol Tree of door de entry point te volgen. Stap 3: Identificeer de password check logica — zoek naar string comparisons (strcmp, strncmp) of custom vergelijkingen. Stap 4: Vind de conditional jump (bijv. JNZ of JE) die bepaalt of de check slaagt of faalt. Stap 5: Patch de jump-instructie — verander JNZ naar JZ (of NOP de hele check) zodat elke input geaccepteerd wordt. Exporteer de gepatched binary en test.
Bron: crackmes.one · Ghidra Documentation · Practical Malware Analysis
OEFENING B.2
HARD
Analyseer een malware sample uit MalwareBazaar
Download een malware sample van MalwareBazaar en analyseer deze in een geïsoleerde omgeving (FlareVM of REMnux). Documenteer: strings analyse, import table, C2-communicatie, en persistence mechanisme. Gebruik zowel statische (Ghidra/IDA) als dynamische (x64dbg/Process Monitor) analyse.
TOON ANTWOORD
Statische analyse: Begin met strings en FLOSS voor string-extractie (inclusief obfuscated strings). Bekijk de import table — imports als CreateRemoteThread, VirtualAllocEx, WriteProcessMemory wijzen op process injection. Dynamische analyse: Draai in sandbox, monitor met Process Monitor (filesystem/registry changes), Wireshark (netwerk), en API Monitor (API calls). Documenteer: Hashes (MD5/SHA256), IOCs (IP-adressen, domeinen, mutexes), gedrag (persistence via registry run keys, scheduled tasks, services), en classificatie (RAT, stealer, loader, etc.).
Bron: MalwareBazaar · Practical Malware Analysis · OALabs

  • Ik kan een malware sample analyseren met statische en dynamische methoden
  • Ik begrijp de basis van exploit development (heap, stack, type confusion)

TRACK C

Application Security.

12+ MAANDEN · DEVELOPMENT SPECIALISATIE

Beveiliging inbouwen in het development proces. Niet alleen bugs vinden na release — security integreren in elke fase van de software lifecycle, van design tot deployment.

C

Security als onderdeel van development

AppSec is waar security en software engineering samenkomen. Je doet code reviews, bouwt security tooling in CI/CD pipelines, en helpt development teams om veiligere software te schrijven — zonder hun velocity te vernietigen.

Kernconcepten

  • Secure Code Review — Handmatige code review voor security-kwetsbaarheden. Begrijp source-sink analyse, taint tracking, en common vulnerability patterns per taal.
  • SAST/DAST/IAST/SCA — Static Application Security Testing, Dynamic AST, Interactive AST, Software Composition Analysis. Begrijp de sterkte en zwakte van elke aanpak.
  • Secure SDLC — Security integreren in de software development lifecycle. Van threat modeling in design tot security testing in CI/CD.
  • Threat Modeling at Scale — STRIDE, PASTA, attack trees. Hoe je threat modeling toepast op grote, complexe systemen zonder dat het een bottleneck wordt.
  • Security Champions — Een netwerk van security-bewuste developers opbouwen. Schaalbare security door ownership te verspreiden.
  • Supply Chain Security — SBOMs (Software Bill of Materials), SLSA framework, dependency scanning. Begrijp de risico's van je supply chain.
  • API Security — OAuth/OIDC flows, JWT validatie, rate limiting, input validatie. APIs zijn het nieuwe aanvalsoppervlak.
Diep Begrip — Waarom de beste AppSec engineers developers zijn

De beste Application Security engineers zijn voormalige developers. Dit is geen toeval — het is een fundamentele eigenschap van het vakgebied.

Effectieve security code review vereist dat je de codebase begrijpt. Je moet weten hoe het framework werkt, waar de data vandaan komt, hoe het getransformeerd wordt, en waar het naartoe gaat. Je moet designpatterns herkennen, begrijpen waarom de developer een bepaalde keuze maakte, en weten waar die keuze tot problemen leidt.

Dit gaat veel verder dan alleen de OWASP Top 10 checken. Elke mid-level pentester kan een SQL injection vinden met een scanner. Maar begrijpen waarom de ORM-laag in deze specifieke configuratie kwetsbaar is voor second-order injection — dat vereist developer-level begrip van de stack.

Daarom is het advies: als je AppSec wilt doen, bouw eerst software. Werk minimaal een jaar als developer. Begrijp CI/CD, begrijp deployment, begrijp hoe teams werken. Dan kun je security advies geven dat developers ook daadwerkelijk willen opvolgen.

TRACK D

Cloud Security.

12+ MAANDEN · INFRASTRUCTURE SPECIALISATIE

Beveilig cloud-native infrastructuur over AWS, Azure, en GCP. Van IAM-beleid tot Kubernetes hardening — de cloud is het nieuwe slagveld en misconfiguratie is de nummer één vijand.

D

Van on-premise naar cloud-native security

Cloud security is fundamenteel anders dan traditionele netwerk security. Het aanvalsoppervlak is de configuratie, niet de firewall. Een verkeerd IAM-beleid kan meer schade veroorzaken dan een zero-day exploit.

Kernconcepten

  • AWS + Azure + GCP Depth — Diepe kennis van minimaal één cloud provider. Begrijp de security-specifieke services, logging, en monitoring mogelijkheden.
  • AWS IAM Deep — Policy evaluation logic, permission boundaries, service control policies, cross-account access. IAM is een eigen discipline.
  • Container Security — Docker internals (namespaces, cgroups, overlay filesystem), runc vulnerabilities, image scanning, runtime security.
  • Kubernetes Attack & Defense — RBAC, network policies, pod security standards, secrets management, admission controllers. Zowel aanvallen als verdedigen.
  • Serverless Security — Lambda/Functions attack surface, cold start security, event injection, over-permissioned execution roles.
  • CSPM/CIEM/CWPP — Cloud Security Posture Management, Cloud Infrastructure Entitlement Management, Cloud Workload Protection Platforms. De tools van het vak.
  • eBPF (Falco, Tetragon) — Kernel-level observability voor runtime security. Detecteer anomaal gedrag op container- en host-niveau.
  • Policy-as-Code — OPA (Open Policy Agent), Kyverno, Sentinel. Definieer en enforceer security policies als code.
Diep Begrip — AWS IAM als eigen discipline

AWS IAM misconfiguratie is de #1 cloud security issue. Dit is niet overdreven — de meeste cloud breaches beginnen met een verkeerd geconfigureerd IAM-beleid.

De reden is dat IAM policy evaluation complex is. AWS evalueert policies in een specifieke volgorde:

Explicit Deny > Explicit Allow > Implicit Deny

Dit klinkt simpel, maar wordt snel complex wanneer je te maken hebt met: identity-based policies, resource-based policies, permission boundaries, session policies, service control policies (SCPs), en VPC endpoint policies. Al deze policy types worden gecombineerd geëvalueerd, en het resultaat is niet altijd intuitief.

Een veelvoorkomende fout: een developer geeft een Lambda functie s3:* rechten "omdat het makkelijker is." Die Lambda heeft nu toegang tot elke S3 bucket in het account — inclusief de bucket met klantdata, backups, en audit logs. Eén SSRF-kwetsbaarheid in die Lambda en je hebt een volledige data breach.

Dit is waarom cloud security professionals IAM als een eigen discipline behandelen. Je moet de evaluation logic begrijpen, least-privilege policies kunnen schrijven, en tools als IAM Access Analyzer, Prowler, en Cloudsplaining kunnen inzetten om misconfiguraties te vinden.

TRACK E

Digital Forensics & Incident Response.

12+ MAANDEN · DEFENSIEVE SPECIALISATIE

Onderzoek compromised systemen, reconstrueer aanvalsketens, en reageer op incidenten. De waarheid ligt in het geheugen, het filesystem, en de logs — je moet het alleen weten te vinden.

E

Van artefact tot tijdlijn

DFIR combineert forensisch onderzoek met operationele incident response. Je analyseert geheugen, disk images, en logs om te begrijpen wat er is gebeurd, wanneer, en door wie. Elke conclusie moet bewijsbaar zijn.

Kernconcepten

  • Memory Forensics Deep — Custom Volatility plugins schrijven, geheugenstructuren begrijpen, hidden processes en injected code detecteren. Het RAM is de ground truth.
  • Windows Artifact Forensics — Registry hives, Event Logs, Prefetch, Amcache, ShimCache, USN Journal, $MFT. Elk artefact vertelt een deel van het verhaal.
  • macOS Forensics — Unified logs, FSEvents, Spotlight metadata, Keychain, APFS snapshots. macOS heeft unieke artefacten die anders werken dan Windows.
  • Mobile Forensics — iOS en Android acquisition, app data analyse, SQLite databases, location data, communication logs.
  • Cloud Forensics — CloudTrail analyse, VPC Flow Logs, container forensics, serverless logs. Forensics in ephemeral environments.
  • Large-Scale Triage — Velociraptor en GRR voor enterprise-brede forensische collectie. Honderd endpoints tegelijk onderzoeken.
  • Expert Witness Skills — Rapportage die standhoudt in de rechtszaal. Chain of custody, bewijsintegriteit, en heldere communicatie van technische findings.
Diep Begrip — Waarom geheugenforensics de 'ground truth' is

Het RAM bevat informatie die nooit naar disk geschreven wordt. Dit maakt geheugenforensics de meest waardevolle — en tegelijkertijd de meest vluchtige — bron van forensisch bewijs.

Voorbeelden van wat alleen in het geheugen leeft:

Decrypted strings: Malware die zijn strings encrypt op disk, decrypteert ze in het geheugen tijdens executie. In een memory dump vind je de plaintext C2 domeinen, credentials, en configuratie die op disk versleuteld zijn.

Injected code: Process injection (via CreateRemoteThread, process hollowing, etc.) laat code uitvoeren in een legitiem process. Op disk bestaat deze code niet — alleen in het geheugen van het doelproces.

Network connections van malware die zijn sporen wist: Zelfs als malware zijn bestanden van disk verwijdert en zijn registry entries opruimt, staan actieve network connections nog in het geheugen. Volatility's netscan plugin vindt deze verbindingen.

Dit is waarom het eerste wat je doet bij een incident een memory dump maken is — voordat je het systeem afsluit, voordat je tools draait, voordat je iets anders doet. Het geheugen is vluchtig: één reboot en het bewijs is weg.

Detection Engineering.

12+ MAANDEN · HYBRIDE SPECIALISATIE

Schrijf code die aanvallen vangt. Detection engineering is de brug tussen red team en blue team — je combineert aanvalskennis met software engineering om detecties te bouwen, testen, en deployen.

F

Software engineering voor security

Detection engineering behandelt detectieregels als code: geschreven in een IDE, getest met attack emulation, gereviewed in pull requests, en gedeployed via CI/CD. Het is software engineering, maar je product is de detectie van kwaadaardig gedrag.

Kernconcepten

  • Detection-as-Code Workflows — Detectieregels als code behandelen: version control, testing, review, deployment. Reproduceerbaar en schaalbaar.
  • Sigma + Splunk + Elastic + Sentinel — Sigma als universeel formaat, geconverteerd naar platform-specifieke query's. Begrijp de sterkte en beperkingen van elk platform.
  • Purple Teaming — Red en blue samenvoegen: voer aanvallen uit en verifieer detectie tegelijkertijd. Itereer tot de detectie betrouwbaar is.
  • Attack Emulation — Atomic Red Team, Caldera, MITRE ATT&CK evaluations. Gestructureerd aanvallen emuleren om detecties te valideren.
  • Careful ML — Machine learning voor anomaly detection, maar met gezond verstand. Begrijp false positive rates, base rate fallacy, en wanneer ML wel en niet zinvol is.
  • Data Engineering — Log parsing, normalisatie, enrichment. De kwaliteit van je detecties is direct afhankelijk van de kwaliteit van je data.
  • Security Data Lakes — Langetermijn opslag van security telemetrie. Snowflake, Databricks, of cloud-native oplossingen voor historische analyse en threat hunting.
Diep Begrip — Detection Engineering als brug tussen Red en Blue

Detection Engineering is het vakgebied dat red team kennis vertaalt naar werkende detecties. Het is de brug tussen offensieve en defensieve security.

Als detection engineer schrijf je code die aanvallen vangt. Maar in tegenstelling tot traditionele SOC-analisten die alerts triagen, bouw je het systeem dat die alerts genereert. Je werkwijze lijkt meer op die van een software engineer:

Je schrijft detectieregels in Sigma (een universeel formaat), test ze met attack emulation (Atomic Red Team, Caldera), reviewt ze in pull requests, en deployt ze via CI/CD pipelines. Elke detectie heeft unit tests: "als ik deze specifieke ATT&CK techniek uitvoer, moet deze detectie afgaan."

Dit is waarom detection engineering de snelst groeiende specialisatie in security is. Organisaties realiseren zich dat handmatige threat hunting niet schaalt. Ze hebben engineers nodig die detecties bouwen als software — onderhoudbaar, testbaar, en continu verbeterend.

De ideale detection engineer heeft drie skills: aanvalskennis (weten wat je moet detecteren), data engineering (de data in de juiste staat krijgen), en software engineering (de detectie betrouwbaar bouwen en deployen).

OEFENING F.1
HARD
Schrijf 5 Sigma rules voor verschillende ATT&CK tactics
Schrijf 5 Sigma rules die elk een andere ATT&CK tactic dekken. Converteer elke regel naar zowel Splunk SPL als Elastic KQL met sigma-cli. Test elke detectie met de bijbehorende Atomic Red Team test.
TOON ANTWOORD
Schrijf Sigma YAML voor deze 5 scenarios: 1. Credential Dumping (TA0006): Detecteer lsass.exe access door niet-standaard processen via Sysmon Event ID 10 (ProcessAccess) met GrantedAccess flags die geheugenlezing toestaan. 2. Lateral Movement (TA0008): Detecteer PsExec-achtig gedrag via service creation (Event ID 7045) met verdachte service namen en executable paden. 3. Persistence via Scheduled Task (TA0003): Detecteer schtasks.exe met /create parameter, focus op taken die executables uitvoeren vanuit verdachte locaties (Temp, AppData). 4. Defense Evasion via Process Injection (TA0005): Detecteer CreateRemoteThread calls (Sysmon Event ID 8) vanuit onverwachte source processen naar high-value targets. 5. Exfiltration via DNS (TA0010): Detecteer ongewoon lange DNS queries (subdomain length > 50 chars) of hoog volume DNS queries naar een enkel domein.

Ethische richtlijn voor Fase 4

In deze fase werk je met geavanceerde technieken — C2 frameworks, malware analyse, exploit development, cloud penetration testing. De grens tussen research en criminaliteit is een dunne lijn, en die lijn heet autorisatie.

Specialisatie brengt verantwoordelijkheid. Hoe dieper je kennis, hoe groter de potentiële schade als je die kennis misbruikt. Maar ook: hoe groter je vermogen om organisaties en mensen te beschermen.

  • Red team technieken alleen uitvoeren met een getekende Rules of Engagement en expliciete autorisatie van de opdrachtgever
  • Malware analyseren in geïsoleerde lab-omgevingen — nooit op productiesystemen of gedeelde netwerken
  • Exploits ontwikkelen voor research en defensieve doeleinden — responsible disclosure als je kwetsbaarheden vindt
  • Cloud security testing alleen op accounts die je bezit of waarvoor je expliciete toestemming hebt
  • Forensisch bewijs behandelen met integriteit — chain of custody respecteren, conclusies baseren op bewijs
  • Detectieregels delen met de community — security is een collectieve inspanning
  • In Nederland: Art. 138ab Sr (computervredebreuk), Art. 350a Sr (beschadiging computergegevens), Art. 139c Sr (aftappen communicatie)
