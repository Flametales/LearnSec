3.1

Security Architectuur & Moderne Defensie

Van perimeter-denken naar assume-breach. Hoe moderne verdediging echt werkt.

Diep Begrip: Waarom Zero Trust niet gewoon ‘meer verificatie’ is

Zero Trust is een architecturale verschuiving, geen product dat je koopt. Het traditionele model vertrouwt alles binnen het netwerk — “castle and moat”. Zero Trust vertrouwt niets impliciet: elke request wordt geverifieerd op basis van identity, device health, context, en least privilege. Google’s BeyondCorp paper (2014) is het origineel: medewerkers werken alsof ze op een onvertrouwd netwerk zitten, want dat IS zo.

Het cruciale inzicht: Zero Trust gaat niet over “meer MFA toevoegen”. Het gaat over het elimineren van implicit trust zones. Een VPN is niet Zero Trust — het creëert juist een nieuwe trust zone. Echte Zero Trust betekent: identity-based access, continuous verification, micro-segmentation, en assume breach op elke laag.

  • Zero Trust — Google’s BeyondCorp paper (2014) + NIST SP 800-207
  • Netwerk segmentatie: macro, micro, identity-based
  • Defense in depth — niet “meer controls” maar layered, elk uitgaande van dat anderen falen
  • MITRE D3FEND — defensieve tegenhanger van ATT&CK
  • NIST SP 800-160 Vol 2 — Cyber Resilience
  • WAF, RASP, NGFW, SASE — wat elk echt doet en waar elk faalt

3.1.1MEDIUM
Zero Trust Architectuur Ontwerp
Ontwerp een Zero Trust architectuur voor een klein bedrijf (50 medewerkers, hybrid cloud). Documenteer identity provider, device trust, segmentatie, en access policies.
Toon antwoord

Kerncomponenten: 1) Identity Provider (Azure AD/Okta) met MFA voor iedereen, 2) Device trust via MDM — alleen managed devices krijgen toegang, 3) Micro-segmentatie — elk applicatie-segment heeft eigen access policies, 4) Continuous verification — session risk scoring op basis van locatie, device health, gedrag, 5) Least privilege — JIT (Just-In-Time) access voor admin taken, 6) Encrypted everywhere — mTLS tussen services, geen plain HTTP intern.

Cruciaal: geen VPN als “trust boundary”. Gebruik een ZTNA-proxy (Cloudflare Access, Zscaler) die elke request evalueert.

3.2

Logging & Detection Engineering

Het diepe deel van defense. 8-10 weken.

Diep Begrip: De Pyramid of Pain

David Bianco’s Pyramid of Pain rangschikt indicatoren van makkelijk (voor aanvallers om te veranderen) naar moeilijk. Van onder naar boven: Hash Values → IP Addresses → Domain Names → Network/Host Artifacts → Tools → TTPs.

Hash-based detectie is de zwakste tier: één byte veranderen in malware = nieuwe hash. IP-detectie is iets beter maar trivially bypassed met nieuwe infra. TTP-detectie (Tactics, Techniques, Procedures) is het moeilijkst maar meest waardevol: het dwingt aanvallers om hun hele methodologie te veranderen, niet alleen hun tooling.

Praktisch: als je SIEM alleen draait op IOC feeds (hashes, IPs, domains), detecteer je alleen bekende dreigingen. Als je detecteert op gedrag (“een proces dat LSASS opent met PROCESS_VM_READ”), vang je elke credential dumper — Mimikatz, ProcDump, custom tools, alles.

Telemetrie bronnen

  • Windows: Event Logs, Sysmon, ETW
  • Linux: auditd, sysmon-for-linux, eBPF (Falco, Tracee)
  • Netwerk: Zeek, Suricata, NetFlow/IPFIX
  • Cloud: CloudTrail, Azure Activity Log, GCP Audit Logs

SIEM — ken er één diep

  • Splunk — SPL is een eigen taal
  • Elastic Security
  • Microsoft Sentinel — KQL wordt must-know
  • Open source: Wazuh, Security Onion

Detection engineering — het ambacht

  • Sigma rules — vendor-agnostische detection taal
  • Detection-as-code: rules in git, getest, peer-reviewed, deployed via CI/CD
  • Pyramid of Pain (David Bianco)
  • ATT&CK-driven detection — map elke detection naar een techniek
  • Detection testing: Atomic Red Team, Caldera

3.2.1HARD
Schrijf een Sigma rule voor Mimikatz detectie
Schrijf een Sigma rule die Mimikatz uitvoering detecteert. Overweeg meerdere detectiemethoden.
Toon antwoord 
title: Mimikatz Execution Detection
logsource:
    category: process_creation
    product: windows
detection:
    selection_name:
        Image|endswith: '\mimikatz.exe'
    selection_cmdline:
        CommandLine|contains:
            - 'sekurlsa::logonpasswords'
            - 'lsadump::dcsync'
            - 'kerberos::golden'
    condition: selection_name or selection_cmdline

Maar dit detecteert alleen de tool bij naam. Een betere detectie is gedragsmatig: Sysmon Event ID 10 (ProcessAccess) waar het target LSASS is met GrantedAccess 0x1010 of 0x1FFFFF. Dit vangt ELKE credential dumper, niet alleen Mimikatz.

Sysmon Configuratie
Configureer Sysmon met SwiftOnSecurity’s template en verifieer dat Event IDs 1, 3, 7, 10, 11 worden gelogd.

3.3

EDR / XDR — Diep

Begrijp hoe endpoint detection echt werkt — en waarom aanvallers het omzeilen.

Diep Begrip: Hoe EDR werkt onder de motorkap

EDR hookt op meerdere niveaus: 1) Usermode hooking — ntdll.dll functies worden gepatcht om via de EDR te lopen. Verouderd maar nog gebruikt. 2) Kernel callbacks — PsSetCreateProcessNotifyRoutine, ObRegisterCallbacks voor process/thread/handle events. 3) ETW Threat Intelligence — een speciale ETW provider die alleen door PPL (Protected Process Light) processen gelezen kan worden. Registreert syscall-niveau events. 4) AMSI — Anti-Malware Scan Interface scant scripts (PowerShell, VBScript, JScript) vóór uitvoering.

Aanvallers omzeilen dit via: direct syscalls (overslaan van ntdll hooks), ETW patching (NtTraceEvent nullen), AMSI patching (AmsiScanBuffer returnt altijd “clean”). De arms race is continu — elke bypass wordt uiteindelijk gedetecteerd, wat nieuwe bypasses drijft.

  • Usermode hooking, kernel callbacks, ETW Threat Intelligence, AMSI
  • Bypass technieken: direct/indirect syscalls, unhooking, ETW patching
  • Sysmon configuratie: SwiftOnSecurity, Olaf Hartong modular
  • osquery / Velociraptor voor fleet visibility

3.3.1MEDIUM
osquery Detection Queries
Installeer osquery en schrijf 3 queries die verdachte activiteit detecteren.
Toon antwoord

1) Unsigned processes: SELECT name, path, pid FROM processes WHERE path NOT IN (SELECT path FROM signature WHERE result='valid');

3) Recent startup items: SELECT name, path, source FROM startup_items WHERE path NOT LIKE '%Microsoft%';

3.4

Threat Intelligence — Echt, Niet Buzzword

Diep Begrip: IOCs vs IOAs vs TTPs

IOCs (Indicators of Compromise): concrete observables — hashes, IPs, domains. Makkelijk te delen, maar triviaal voor aanvallers om te veranderen. Een hash-based IOC is waardeloos zodra de aanvaller één byte wijzigt.

IOAs (Indicators of Attack): gedragspatronen die wijzen op een lopende aanval — “een proces dat PowerShell spawnt en base64-encoded commands uitvoert”. Moeilijker te omzeilen omdat het gedrag beschrijft, niet artefacten.

TTPs (Tactics, Techniques, Procedures): de methodologie van een threat actor. “Gebruikt spearphishing met macro-enabled documents voor initial access, gevolgd door Cobalt Strike voor C2”. Het moeilijkst te veranderen — het vereist dat de aanvaller zijn hele operatie herschrijft.

Je detectiestrategie zou moeten focussen op de top van de Pyramid of Pain: TTPs en Tools. IOC feeds zijn nuttig voor quick wins, maar het is geen strategie.

  • MITRE ATT&CK — internaliseren, niet alleen kennen
  • Diamond Model (adversary, capability, infrastructure, victim)
  • Cyber Kill Chain (Lockheed Martin)
  • TI lifecycle: direction → collection → processing → analysis → dissemination
  • MISP voor sharing, STIX/TAXII als standaard

3.5

Incident Response — Praktijk-Niveau

Diep Begrip: Windows forensische artefacten

Prefetch (C:\Windows\Prefetch): bewijst dat een programma is uitgevoerd, inclusief timestamps en geladen DLLs. Aanvallers wissen het soms — de afwezigheid ervan is ook een indicator.

ShimCache (AppCompatCache in registry): logt elke executable die Windows overweegt uit te voeren, zelfs als het niet daadwerkelijk runt. Overleeft reboots.

AmCache (C:\Windows\AppCompat\Programs\Amcache.hve): SHA1 hash van uitgevoerde programma’s, pad, eerste executie timestamp. Goudmijn voor incident response.

$MFT (Master File Table): metadata van elk bestand op NTFS — creatiedatum, modificatiedatum, bestandsnaam. Timestomping detectie: vergelijk $STANDARD_INFORMATION timestamps met $FILE_NAME timestamps.

Combineer deze artefacten voor een compleet beeld van programma-executie. Geen enkel artefact is volledig — de kracht zit in correlatie.

Frameworks

  • NIST SP 800-61r2
  • SANS PICERL: Prepare, Identify, Contain, Eradicate, Recover, Lessons

Disciplines

  • Memory forensics — Volatility 3, MemProcFS
  • Disk forensics — Autopsy, KAPE
  • Timeline analysis — plaso/log2timeline
  • Live response — Velociraptor
  • Network forensics — Wireshark + Zeek + Arkime

3.6

Malware Analyse — Voorbij Intro

8-10 weken. Van statische analyse tot YARA rules.

Diep Begrip: PE format internals

Een PE (Portable Executable) bestand is gestructureerd als: DOS Header → PE Signature → COFF Header → Optional Header → Section Table → Sections. Elke sectie vertelt een verhaal:

  • .text — executable code. Hoge entropy = mogelijk geobfusceerd of gepackt.
  • .data — geïnitialiseerde data (strings, globals).
  • .rsrc — resources (iconen, maar ook embedded executables, configs).
  • .rdata — read-only data, inclusief import/export tables.

De Import Address Table (IAT) is cruciaal: VirtualAllocEx + WriteProcessMemory + CreateRemoteThread = klassieke process injection. InternetOpenUrl + CreateService = backdoor met HTTP C2 en persistence. Leer imports lezen als een verhaal over wat de malware doet.

Statische analyse

  • PE/ELF format internals, strings, imports analysis
  • Ghidra mastery (gratis, NSA)
  • IDA Free · Binary Ninja

Dynamische analyse

  • Sandboxes: Any.Run, Hybrid Analysis
  • Lab: FLARE-VM (Windows), REMnux (Linux)
  • Debuggers: x64dbg, WinDbg
  • YARA — schrijf rules die families vangen

3.6.2HARD
YARA Rules Schrijven
Schrijf 3 YARA rules: hash-based, string-based, en behavioral.
Toon antwoord 
rule hash_based {
  condition:
    hash.sha256(0, filesize) == "abc123..."
}

rule string_based {
  strings:
    $s1 = "CreateRemoteThread"
    $s2 = "VirtualAllocEx"
    $url = /https?:\/\/[a-z0-9\-\.]+\.xyz\//
  condition:
    uint16(0) == 0x5A4D and all of ($s*) and $url
}

rule behavioral_injection {
  strings:
    $api1 = "OpenProcess"
    $api2 = "VirtualAllocEx"
    $api3 = "WriteProcessMemory"
    $api4 = "CreateRemoteThread"
  condition:
    uint16(0) == 0x5A4D and all of them
}

3.7

Threat Hunting

Diep Begrip: Hypothesis-driven hunting

Threat hunting is NIET alert triage. Het is proactief zoeken naar dreigingen die je detecties gemist hebben. Het verschil: alert-driven = reactief (“SIEM zegt X”), hypothesis-driven = proactief (“als een aanvaller Kerberoasting deed, zou ik Y zien in Z databron”).

Een goede hunting hypothesis volgt dit patroon: “Gegeven [threat intelligence/kennis], als een aanvaller [techniek] gebruikt, zou ik [observeerbaar artefact] zien in [databron], en ik kan dit vinden door [query/methode].”

TaHiTI (Targeted Hunting integrating Threat Intelligence) is een Nederlandse methodologie, ontwikkeld door de bankensector. Het formaliseert dit proces.

  • Hypothesis-driven (niet alert-driven) hunting
  • ATT&CK-driven hunts
  • TaHiTI methodologie — Nederlandse oorsprong
  • KQL en SPL vloeiend
  • Hunting in network data met Zeek

Capstone — Bouw Je Eigen SOC

Diep Begrip: Waarom een home SOC je onderscheidt

Een home SOC bouwen dwingt je om elk stuk van de defensieve pipeline te begrijpen: log collection, normalization, detection, alerting, en response. De meeste SOC-analisten gebruiken tools zonder te begrijpen wat eronder zit. Door het zelf te bouwen — Wazuh als SIEM, Sysmon als telemetrie, Sigma rules als detecties, Atomic Red Team als test framework — begrijp je elke laag.
